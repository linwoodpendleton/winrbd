# core/

The portable C core: Ceph wire protocol (monitor client, cephx, msgr2, later OSDMap, CRUSH, OSD object I/O) and RBD format-2 image access. No platform dependencies: sockets and time are data flowing through a pump API, memory is handed over once, and the only calls from the core into a host are `random` and `log`.

License: MIT (see `COPYING.MIT`); every file starts with `/* SPDX-License-Identifier: MIT */`. Exception: `core/crush_ln/` holds the two LGPL-licensed CRUSH log tables, copied unchanged from Ceph with their notice (`COPYING.LGPL-2.1`; see [`crush_ln/README.md`](crush_ln/README.md)); nothing else may go there. Apart from those two tables nothing here is copied from Ceph, iPXE, WNBD or the Linux kernel: it is written from the spec notes in `docs/spec/`.

| 6 and later (OSD sessions, RBD, secure mode) | not started; `docs/design/core-architecture.md` section 10 records the hooks |

What a host gets today: create a client from a `wr_config`, a cluster description (monitor addresses, user name, key) and two memory regions; drive it with `wr_client_run()`; move bytes with `wr_conn_*`; read events and, with maps off, raw map messages, or, with maps on (`wr_config_enable_maps()` after a profile), track pools by name (`wr_client_pool_track`) and place objects (`wr_client_map_target`, `wr_map.h`). The client logs in to a monitor (hunting across the monitor list, backing off, re-authenticating after a lost session), keeps the session alive, renews its tickets before they expire and subscribes to `monmap` and `osdmap`. All of it is exercised against a simulated monitor and the committed vectors and public captures; `harness/host/tools/wr-monprobe` is the tool that points the same code at a real cluster (the lab Ceph v20.2.5 in `harness/lab/`).

## Layout

```
core/
  include/winrbd/       the PUBLIC headers: all a host includes (winrbd.h is the umbrella)
  src/<module>/         the implementation; wri_*.h are internal interfaces between modules
  sources.txt           the list of C files, generated by tools/gen_sources.sh (iPXE make and msbuild read it)
```

## Rules (what the build checks)

- ISO C99, headers `<stddef.h>` and `<stdint.h>` only; no allocation, no global mutable state, no recursion, no floating point, no VLAs. Memory comes from the host in two regions (`arena`, `bulk`) at create; every length read from the wire is compared with a budget in `wr_config` first.
- Every `.c` file has a unique basename (iPXE derives object names from it). Files stay under about 500 lines (`core.docs` fails a file above 500). No recursion; the deepest direct call chain is 13 frames and the largest stack along any chain is 3,064 bytes (gcc 13 -O2 call graph, summed frame sizes; that chain is the incremental apply of the map store, which decodes the full map embedded in an incremental and audits its rules; the renewal chain is the deepest, and the worst chain of the wire half, through the monitor client, is 2,096 bytes), measured by `harness/tests/ci-docs-hardening/check_callgraph.py` in the CI job `static-limits` (and by the ctest `map.hardening`), which fails above 14 frames or 3,328 bytes, and above a budget of its own for each entry point of the map half (measured / budget, bytes of static frames: placement `wr_client_map_target` 1,528 / 1,664 and 10 frames deep, store step `wri_mapstore_step` 2,792 / 3,072, full-map decode 1,720 / 1,920, incremental apply 2,488 / 2,752, CRUSH decode 568 / 640, rule interpreter 696 / 768). The stack limit was 2 KiB before part B (the wire half measures 2,096 bytes by the corrected measurement, so it was already over) and is 3.25 KiB now: the map chains are heavier than the first measurement said (it read the sizes in directory order and let a function a file only calls overwrite the size of its definition, so it reported 1,632 bytes), and the biggest frames of the worst chain are `probe_legacy` 640, `wri_osdmap_apply_inc` 768 and `wri_osdmap_decode_full` 608 bytes (open item: shrink them before the iPXE stack is measured in Phase 2). Calls through function pointers (host callbacks, the crypto override table, the map store's I/O hooks, 16 bytes each) are not followed.
- `-Wall -Wextra -Werror` plus the long list in `harness/cmake/WrWarnings.cmake`, on gcc and clang, with and without `-DWR_SANITIZE=address,undefined`; `-Wframe-larger-than=1024`.
- Mechanical gates in ctest: `core_sources_in_sync`, `core_no_libc` (the library may reference only `memcpy/memmove/memset` and compiler arithmetic helpers; equality is `wri_ct_memeq`, so there is no `memcmp` and no `bcmp`), `core_no_globals` (no `.data`, `.bss`, COMMON or TLS), `core_freestanding`, `core_freestanding_os`, `core_freestanding_m32` (every core file compiled as ISO C99 with `-ffreestanding -nostdinc` and only the compiler's own `<stddef.h>` / `<stdint.h>`, then linked with `-nostdlib` next to a stub that defines `memcpy`, `memmove` and `memset` and nothing else: the link fails if the core needs any other symbol; this is what an iPXE or kernel build sees; `-O2`, `-Os` and 32-bit `-m32 -Os`), `core.budgets` (footprint of each profile, guard bands around the exactly sized regions, an oversized map message), `core.docs` (this file and `harness/README.md` against the tree: footprint table, file sizes, fuzz seeds, test names, licence tags, the CI workflow). The two object gates also run in CI on optimised builds (Release and MinSizeRel, gcc and clang) and on the 32-bit and iPXE-flag objects.
- Compiler note: the core never calls `memcmp` (it uses `wri_ct_memeq`), so clang at -O2 and above, which rewrites `memcmp(a, b, n) == 0` into a call to `bcmp`, has nothing to rewrite and the object code needs no flag. A host that overrides `WR_MEMCMP` is not affected either: nothing in the core uses it.
- Compile-only targets: `wr_core_m32` (32-bit `size_t` and pointers, as on i386 iPXE), `wr_core_ipxe_flags` (the iPXE build's own warning set, `-ffreestanding -Os`) and `wr_header_check` (each header compiles as the first include of a translation unit).

**What the review and the runs found.** Fixed during the module reviews: a size wrap in `wri_mapbuild_crush_room` that a map could steer into a negative `memset` (high), a 28-second loop in `wri_crush_check` for a hostile `choose_args` row count (low), a pool tracked after the first map that never resolved on a quiet cluster (medium), an incremental whose new slot overlapped its own input (low), and a handful of foreign-fsid, cache-key and budget-validation gaps. Found by this hardening pass: nothing in the core. MemorySanitizer reported four places in tests and fuzz targets that pass an uninitialised `wr_errinfo` (the core reads its `status` to keep the first failure, so the contract is that the caller zeroes it): `harness/test/test_map_vec_err.c`, `test_osdmap_tab.c`, `test_osdmap_inc.c` and `harness/fuzz/fuzz_osdmap_inc.c` (the initial decode of the held map); they are harmless under ASan and are open items for the owners of those files. The clean-copy build matrix at the end (gcc and clang, Debug and Release, with and without ASan and UBSan) found two harness problems and no core problem: `harness/src/winrbd-mapwatch.c` did not build with gcc in Release (the fortified `read()` of its input buffer, whose room was computed in a way gcc could not bound; it is now clamped), and a race in the part A test `host.loop` (it checked for a cut-short send right after the last injected failure, which fails when the machine is busy; it now waits for one). The scrub check of the map vectors named a user, a host and a customer address in its own patterns; they are now generic.

## Memory footprint

`wr_client_mem_required()` returns the exact sizes of the two regions; the engine takes nothing after create. Measured by `harness/test/test_core_budgets.c` (which fails if a product profile exceeds its budget):

| Profile | arena | bulk | documented budget (arena / bulk) |
|---|---|---|---|
| `wr_config_profile_ipxe` | 108 KiB | 1030 KiB | 128 KiB / 1 MiB + 16 KiB |
| `wr_config_profile_kernel` | 464 KiB | 8198 KiB | 512 KiB / 8 MiB + 32 KiB |
| `wr_config_profile_harness` | 2.4 MiB | 32 MiB | (sanity cap 4 MiB / 40 MiB) |

With the OSD map module on (`wr_config_enable_maps()` on top of a profile: two map slots in the bulk, the placement cache in the arena; `test_core_budgets` checks these rows too):

| Profile | arena | bulk | documented budget (arena / bulk) |
|---|---|---|---|
| `ipxe + maps` | 113 KiB | 1542 KiB | 128 KiB / 1600 KiB |
| `kernel + maps` | 502 KiB | 10246 KiB | 512 KiB / 10304 KiB |
| `harness + maps` | 3.0 MiB | 40 MiB | (sanity cap 4 MiB / 48 MiB) |

The arena holds the hot state (connections, handshake transcripts, keys, tickets); the bulk holds the raw map message slots (`mon_msg_cap` each) and, with maps on, the two map slots (`map_slot_bytes` each: 256 KiB, 1 MiB, 4 MiB). Every client embeds the map store's own state (about 2 KiB of the arena, inert when maps are off), which is why the plain arena rows are 2 KiB above the figures of milestones 1 to 3; the placement cache costs 152 bytes per entry (`map_pg_cache`). A map that does not fit its slot is `WR_E_MAP_BUDGET`: fatal for the first map (`WR_EV_FATAL`), a counted failure with the held map still serving afterwards. The numbers are measured on a 64-bit host; the 32-bit iPXE build has smaller pointers, so its footprint is not larger. The test hands the engine regions of exactly the announced size inside guard bands, so a write past the end is a failure, and `core.docs` fails when the plain rows drift from the measured numbers. Details: `docs/design/core-architecture.md` sections 5 and 15.3.

## Hosts

| Host | Where | State |
|---|---|---|
| Linux user space (the harness) | `harness/host/` | the system helpers are done; the socket pump and `wr-monprobe` are in the tree |
| iPXE (no threads, 4 MiB heap, `umalloc` for big buffers) | `ipxe/` glue, Phase 2 | not started; the core already compiles with the iPXE flags and for 32 bits |
| Windows kernel storport driver (non-paged pool, no CRT) | `windows/`, Phase 3 | not started; the core uses no CRT and no pageable allocation by construction |

## Build and test

From a clean checkout, with gcc or clang (CMake 3.16 or newer; Ninja optional; OpenSSL development files, Python 3 and `gcc-multilib` are optional and make more tests run instead of skip):

```sh
cmake -S harness -B build && cmake --build build && ctest --test-dir build --output-on-failure
```

That is the whole check: 108 tests, of which 106 run anywhere. The two that need the lab Ceph cluster (`lab.mon` and `lab.map`, label `lab`, need `WR_LAB_*` in the environment) skip by themselves; `ctest -LE lab` leaves it out. [.github/workflows/core.yml](../.github/workflows/core.yml) runs exactly this with gcc and clang, Debug and Release, on `ubuntu-latest`; [.github/workflows/harness.yml](../.github/workflows/harness.yml) adds the sanitizer, 32-bit, iPXE-flag, call-depth and libFuzzer-smoke jobs. Warnings are errors in every one of them.

More in [harness/README.md](../harness/README.md) (options, one test, the sanitizers, long fuzz runs). In short: `cmake -S harness -B build/harness && cmake --build build/harness -j && ctest --test-dir build/harness --output-on-failure`. Design and implementation plan: [docs/design/core-architecture.md](../docs/design/core-architecture.md).
