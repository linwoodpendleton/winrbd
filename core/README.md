# core/

The portable C core: Ceph wire protocol (monitor client, cephx, msgr2, later OSDMap, CRUSH, OSD object I/O) and RBD format-2 image access. No platform dependencies: sockets and time are data flowing through a pump API, memory is handed over once, and the only calls from the core into a host are `random` and `log`.

License: MIT (see `COPYING.MIT`); every file starts with `/* SPDX-License-Identifier: MIT */`. Exception: `core/crush_ln/` holds the two LGPL-licensed CRUSH log tables, copied unchanged from Ceph with their notice (`COPYING.LGPL-2.1`; see [`crush_ln/README.md`](crush_ln/README.md)); nothing else may go there. Apart from those two tables nothing here is copied from Ceph, iPXE, WNBD or the Linux kernel: it is written from the spec notes in `docs/spec/`.

## Status

**Phase 1, milestones 1 to 8 are implemented, tested and hardened: the wire half (milestones 1 to 3), the map half (the OSD map, CRUSH, object placement, behind `wr_config_enable_maps()`) and the object I/O half (OSD sessions and object I/O, RBD format 2 open, block I/O, behind `wr_config_enable_osd()`), the last one tested against simulated OSDs and, through the Linux host and the `wr-rbd` tool, against the real lab cluster with both key types, including an OSD killed and restarted, an OSD marked out and in, and primaries moved by `pg-upmap` while the core does I/O: no byte differs from the model or from the stock `rbd export` (below). Part D, the byte comparison with krbd (milestone 9) and secure mode (milestone 11), is implemented, tested as code (below and the part D section) and was shown on the lab cluster: zero byte differences against a kernel-mapped device in crc mode (40,641 operations) and in secure mode (83,917 operations), the live secure matrix 202 checks, 0 failures. What is not shown yet is the exit run of Phase 1, the long run with an OSD and a monitor daemon killed under the krbd comparison, so Phase 1 is not closed (roadmap).**

What a host gets today: create a client from a `wr_config`, a cluster description (monitor addresses, user name, key) and two memory regions; drive it with `wr_client_run()`; move bytes with `wr_conn_*`; read events and, with maps off, raw map messages, or, with maps on (`wr_config_enable_maps()` after a profile), track pools by name (`wr_client_pool_track`) and place objects (`wr_client_map_target`, `wr_map.h`). The client logs in to a monitor (hunting across the monitor list, backing off, re-authenticating after a lost session), keeps the session alive, renews its tickets before they expire and subscribes to `monmap` and `osdmap`. With the OSD client on (`wr_config_enable_osd()` after `wr_config_enable_maps()`), open an RBD image (`wr_image_open`, `wr_image.h`), submit block requests, run the engine, and pull the finished requests with `wr_client_next_done()`; the OSD connections arrive as ordinary `WR_ACT_CONNECT` actions with `osd_connect_timeout_ms` as their timeout, and the host calls `wr_client_run()` after every open, submit, cancel and close (design 28). All of it is exercised against a simulated monitor and the committed vectors and public captures; `harness/host/tools/wr-monprobe` is the tool that points the same code at a real cluster (the lab Ceph v20.2.5 in `harness/lab/`).

## Rules (what the build checks)

- ISO C99, headers `<stddef.h>` and `<stdint.h>` only; no allocation, no global mutable state, no recursion, no floating point, no VLAs. Memory comes from the host in two regions (`arena`, `bulk`) at create; every length read from the wire is compared with a budget in `wr_config` first.
- Every `.c` file has a unique basename (iPXE derives object names from it). Files stay under about 500 lines (`core.docs` fails a file above 500). No recursion; the deepest direct call chain is 17 frames (the limit; since part D it is the AUTH_SIGNATURE frame going out in secure mode, from the handshake down to the GHASH multiplication, 1,304 bytes of stack; before it was 14, a failed image cancelling its operations down to the session reset, see the part C section) and the largest stack along any chain is 3,064 bytes (gcc 13 -O2 call graph, summed frame sizes; that chain is the incremental apply of the map store, which decodes the full map embedded in an incremental and audits its rules; the worst chain of the wire half, through the monitor client, is 2,096 bytes), measured by `harness/tests/ci-docs-hardening/check_callgraph.py` in the CI job `static-limits` (and by the ctests `map.hardening` and `osd.hardening`), which fails above 17 frames or 3,328 bytes, and above a budget of its own for each entry point of the map half, of the object I/O half (the latter in the part C section) and of secure mode (the part D section) (measured / budget, bytes of static frames: placement `wr_client_map_target` 1,528 / 1,664 and 10 frames deep, store step `wri_mapstore_step` 2,792 / 3,072, full-map decode 1,720 / 1,920, incremental apply 2,488 / 2,752, CRUSH decode 568 / 640, rule interpreter 696 / 768). The stack limit was 2 KiB before part B (the wire half measures 2,096 bytes by the corrected measurement, so it was already over) and is 3.25 KiB now: the map chains are heavier than the first measurement said (it read the sizes in directory order and let a function a file only calls overwrite the size of its definition, so it reported 1,632 bytes), and the biggest frames of the worst chain are `probe_legacy` 640, `wri_osdmap_apply_inc` 768 and `wri_osdmap_decode_full` 608 bytes (open item: shrink them before the iPXE stack is measured in Phase 2). Calls through function pointers (host callbacks, the crypto override table, the map store's I/O hooks, 16 bytes each) are not followed, except the one that matters for the reply path: the msgr2 connection handing a complete message to the upper layer's table, which `--link` adds to the graph.
- `-Wall -Wextra -Werror` plus the long list in `harness/cmake/WrWarnings.cmake`, on gcc and clang, with and without `-DWR_SANITIZE=address,undefined`; `-Wframe-larger-than=1024`.
- Mechanical gates in ctest: `core_sources_in_sync`, `core_no_libc` (the library may reference only `memcpy/memmove/memset` and compiler arithmetic helpers; equality is `wri_ct_memeq`, so there is no `memcmp` and no `bcmp`), `core_no_globals` (no `.data`, `.bss`, COMMON or TLS), `core_freestanding`, `core_freestanding_os`, `core_freestanding_m32` (every core file compiled as ISO C99 with `-ffreestanding -nostdinc` and only the compiler's own `<stddef.h>` / `<stdint.h>`, then linked with `-nostdlib` next to a stub that defines `memcpy`, `memmove` and `memset` and nothing else: the link fails if the core needs any other symbol; this is what an iPXE or kernel build sees; `-O2`, `-Os` and 32-bit `-m32 -Os`), `core.budgets` (footprint of each profile, guard bands around the exactly sized regions, an oversized map message), `core.docs` (this file and `harness/README.md` against the tree: footprint table, file sizes, fuzz seeds, test names, licence tags, the CI workflow). The two object gates also run in CI on optimised builds (Release and MinSizeRel, gcc and clang) and on the 32-bit and iPXE-flag objects.
- Compiler note: the core never calls `memcmp` (it uses `wri_ct_memeq`), so clang at -O2 and above, which rewrites `memcmp(a, b, n) == 0` into a call to `bcmp`, has nothing to rewrite and the object code needs no flag. A host that overrides `WR_MEMCMP` is not affected either: nothing in the core uses it.
- Compile-only targets: `wr_core_m32` (32-bit `size_t` and pointers, as on i386 iPXE), `wr_core_ipxe_flags` (the iPXE build's own warning set, `-ffreestanding -Os`) and `wr_header_check` (each header compiles as the first include of a translation unit).

### Part D: the krbd comparison and secure mode

Milestone 9 (the comparison engine and its tool) and milestone 11 (secure mode) were written as 22 modules in ten waves against frozen interfaces ([design sections 32 to 41](../docs/design/core-architecture.md)), each reviewed by a second reader with mutation tests, and then closed as a unit by the checks below (module `secure-hardening`, design section 41.3). | Profile | arena | bulk | documented budget (arena / bulk) |
|---|---|---|---|
| `ipxe + maps + osd` | 257 KiB | 2566 KiB | 264 KiB / 2624 KiB |

The OSD client alone costs (the difference to the same profile with maps only): ipxe 143 KiB of arena (the profile's 4 connection slots become 8 and its handshake transcript pairs 1 become 2: the buffers of a connection are the dominant part) and 1 MiB of bulk (the zombie area); kernel 945 KiB and 8 MiB; harness 7.5 MiB and 16 MiB. The 4 MiB iPXE heap holds the arena only: 6 % of it (the bulk is `umalloc()`). The operation table is 576 bytes per slot, a session 160 bytes plus its front buffer and its backoff table, an image about 650 bytes plus its snapshot context and control buffers, a request 80 bytes, a connection slot with its buffers the same as for the monitor's. Role-specific connection buffers (an OSD session needs a fraction of what a monitor session does) are the first optimisation if the iPXE heap measurement asks for it.

**The iPXE arena budget with the OSD client was raised from 256 KiB to 264 KiB by the secure-mode glue (module client-glue-sec), deliberately.** Part D added 1,440 bytes to that configuration: the seam of the secure codec (three pointers per connection, 192 bytes for 8 connections), the connection secret every cephx handshake context may hold between AUTH_DONE and the switch (136 bytes in each of 9 contexts) and the engine's own secure-mode fields; the profile had stood at 255.8 KiB with 192 bytes of room. 264 KiB is 6.4 % of the 4 MiB iPXE heap (it was 6.25 %). With the default policy (`WR_MODE_CRC_ONLY`) that is all secure mode costs; no slot and no bounce buffer is reserved.

With secure mode on top (`wr_config_enable_secure()` with any policy that may end in secure, here `WR_MODE_STOCK`; `test_core_budgets` checks these rows): the arena grows by one `wri_m2s_slot` (1,688 bytes: the key schedule, the nonces, the receive stage and the transmit stream record of one connection) and one bounce buffer (`sec_tx_chunk`: 4 KiB iPXE, 16 KiB kernel, 64 KiB harness) for **every** connection slot, so an idle build pays for the connections it could have; the bulk does not change. A host that wants a smaller bill lowers `sec_tx_chunk` (down to 256 bytes) or `osd_sessions`.

| Profile | arena | bulk | documented budget (arena / bulk) |
|---|---|---|---|
| `ipxe + maps + osd + secure` | 302 KiB | 2566 KiB | 308 KiB / 2624 KiB |
| `kernel + maps + osd + secure` | 1767 KiB | 18438 KiB | 1792 KiB / 18496 KiB |
| `harness + maps + osd + secure` | 13.8 MiB | 56 MiB | (sanity cap 15 MiB / 64 MiB) |

The arena holds the hot state (connections, handshake transcripts, keys, tickets); the bulk holds the raw map message slots (`mon_msg_cap` each) and, with maps on, the two map slots (`map_slot_bytes` each: 256 KiB, 1 MiB, 4 MiB). Every client embeds the map store's own state (about 2 KiB of the arena, inert when maps are off), which is why the plain arena rows are 2 KiB above the figures of milestones 1 to 3; the placement cache costs 152 bytes per entry (`map_pg_cache`). A map that does not fit its slot is `WR_E_MAP_BUDGET`: fatal for the first map (`WR_EV_FATAL`), a counted failure with the held map still serving afterwards. The numbers are measured on a 64-bit host; the 32-bit iPXE build has smaller pointers, so its footprint is not larger. The test hands the engine regions of exactly the announced size inside guard bands, so a write past the end is a failure, and `core.docs` fails when the plain rows drift from the measured numbers. Details: `docs/design/core-architecture.md` sections 5 and 15.3.

## Build and test

From a clean checkout, with gcc or clang (CMake 3.16 or newer; Ninja optional; OpenSSL development files, Python 3 and `gcc-multilib` are optional and make more tests run instead of skip):

```sh
cmake -S harness -B build && cmake --build build && ctest --test-dir build --output-on-failure
```

That is the whole check: 233 tests, of which 228 run anywhere (with the sanitizers 231 are registered and 225 run: they do not register the two object-code gates, and the Valgrind drive skips there). The five that need the lab Ceph cluster (`lab.exit`, `lab.map`, `lab.mon`, `lab.rbd` and `lab.secure`, label `lab`, need `WR_LAB_*` in the environment) skip by themselves; `ctest -LE lab` leaves them out. A few tests are slow by design (the secure peers of the host tests use the independent GCM of the simulators): the plain Debug suite takes about 15 minutes at `-j 4` on 8 cores, and with the sanitizers the two serial host tests with secure peers take 4 to 7 minutes each. [.github/workflows/core.yml](../.github/workflows/core.yml) runs exactly this with gcc and clang, Debug and Release, on `ubuntu-latest`; [.github/workflows/harness.yml](../.github/workflows/harness.yml) adds the sanitizer, 32-bit, iPXE-flag, call-depth and libFuzzer-smoke jobs. Warnings are errors in every one of them.
