# harness/

The Linux user-space harness that hosts `core/`: the CMake build of the core as a static library, the unit tests and fuzz targets, the Linux host (sockets pump), and the tools and scripts around the lab cluster. It lets us develop and debug the protocol code without crashing a kernel, and (milestone 9) compare bytes read through the core against Linux krbd on the same image.

## Status

**The build, the unit tests, the simulators, the fuzz targets and the CI workflow work for Phase 1 milestones 1 to 8 and, since part D, for the krbd comparison and secure mode (milestones 9 and 11: done, and shown on the lab cluster by the krbd comparison and the live secure matrix; the long run with an OSD and a monitor killed under it is not reported yet), and the decoder half of milestone 10 covers the OSD map, CRUSH, placement and the whole object I/O half (OSD messages, sessions, the request engine, RBD open and block I/O), proved against the live lab cluster, including a killed OSD and map changes under I/O.** 254 ctest tests (249 without the five lab ones, which skip without a cluster; 247 with the sanitizers, which do not register the two object-code gates nor the five Phase 2 gates that compile the core for iPXE themselves (`core_ipxe_headers_*`, `core_callgraph_*`, `gates.selftest`), and of which the Valgrind drive skips: the sanitizer runtimes do not run under Valgrind): unit tests of every core module (the OSD map, CRUSH, placement and map store modules and the whole object I/O half: `osd.*`, `rbd.*`, `client.osd.*`, the simulated OSD `sim.osd`, the host loop with OSDs and the `wr-rbd` tool included), the capture replays, the vector tests of the lab's maps (`map.vec.*`, `vectors_mapb_check`), the oracle tool (`oracle.cli` and the self-test of its comparison script), the live placement vectors (`place.live`, `vectors_placement_check`), the captures of the core's own image I/O against a real OSD (`imgio.replay`, `vectors_imgio_check`, `vectors_imgio_selftest`), the mechanical gates (no libc, no globals, freestanding link), the footprint test, the documentation check, the hardening check of part B (`map.hardening`), the hardening check of part C (`osd.hardening`), the hardening check of part D (`secure.hardening`) and a seed replay of every fuzz target. The live lab tests (`harness/lab`, label `lab`: `lab.mon`, `lab.map`, `lab.rbd` and `lab.secure`) need the lab cluster and are not part of the default run. The comparison with Ceph's own tools on the lab (`tools/map_oracle_lab.sh`) is a script run on the lab VM, not a ctest, and so is the live placement proof (`tools/map_placement_lab.py` drives the cluster while the whole client `winrbd-mapwatch` follows it; its vectors are replayed offline by `place.live`). The object I/O half has its live matrix in `lab/live-rbd.sh` (the core through the `wr-rbd` tool against the lab, the stock `rbd` and `rados` as the oracle) and its fault run in `tools/osd_fault_lab.sh` (an OSD killed, marked out and in, and primaries moved by `pg-upmap` while the core does random I/O, every byte compared with a model and with `rbd export`); both are scripts run in the lab VM, not ctests.

**Part D (the comparison with krbd and secure mode, milestones 9 and 11) is in the tree as code and tests: unit tests of the constant-time crypto (`crypto.aesct`, `crypto.ghash`, `crypto.gcm`, `crypto.pgcm`, the Valgrind and read-only-data checks `crypto.ct.*`, each against an independent reference and, where OpenSSL is present, against OpenSSL), of the secure framing and its switch (`m2.sec.*`, `m2.conn.sec.*`, `m2.modes`), of the client glue (`client.sec.*`), of the simulator's secure peer (`sim.sec.*`), of the AES-NI hook (`host.gcm.aesni`), of the host loop and the tool with secure peers (`host.loop.sec`, `host.tool.rbd.sec`), the replay of the core's own secure sessions captured against the real cluster (`m2.sec.replay`, `vectors_secure_check`, `vectors_secure_selftest`), the comparison engine and its tool (`host.cmp`, `host.cmp.edges`, `host.tool.krbdcmp`, `krbdcmp.selftest`), the dry runs of the two lab scripts (`secure.live.dry`, `securelive.selftest`) and `ci26.selftest`; five new fuzz targets; the hardening check `secure.hardening`. What the lab showed (numbers in the roadmap and in [core/README.md](../core/README.md)): 124,558 operations of the comparison against krbd in crc and in secure mode with 0 byte differences, `secure-live.sh` 202 checks with 0 failures, and 27 fuzz targets of 8 CPU hours each with no finding. What is not shown yet, and cannot be shown by a unit test: the same comparison with an OSD and a monitor daemon killed under it, the exit run of Phase 1 (`docs/design/core-architecture.md` section 40); the roadmap does not close Phase 1 before it has reported.**

**Phase 2 (the iPXE driver, `docs/design/ipxe-driver.md`) added three portable core modules and the gates that keep the core buildable by iPXE.** Modules: the rBFT handoff table codec (`handoff`, `handoff.vec`, `handoff.vectors_in_sync`, the fuzz target `fuzz_handoff`), the `rbd://` URL parser (`rburl`, the fuzz target `fuzz_rburl`) and the readahead cache (`ra`, and `ra.sim`, which drives it against the whole engine over the simulated cluster). Gates (module harness-gates; what each checks is in the "Gates for the iPXE build" section below): `ipxe.check`, `core_std_c`, `core_ipxe_headers_i386`, `core_ipxe_headers_x86_64`, `core_callgraph_i386`, `core_callgraph_x86_64` and their self-test `gates.selftest`. The harness has no test of the iPXE glue itself: that is built and self-tested by `ipxe/tools/build.sh` (see `ipxe/README.md`), and its live tests need a QEMU guest and the lab cluster.

## Build and test

Needs CMake 3.16+ and gcc or clang (C99). Optional: OpenSSL development files (differential crypto tests, skipped when absent), Python 3 (the pcap replay test, skipped when absent), `gcc-multilib` (the 32-bit compile check, skipped when absent).

```sh
cmake -S harness -B build/harness -DCMAKE_BUILD_TYPE=Debug
cmake --build build/harness -j
ctest --test-dir build/harness --output-on-failure
```

Options (see the header of [CMakeLists.txt](CMakeLists.txt)): `-DWR_SANITIZE=address,undefined`, `-DWR_FUZZ=ON` (clang, libFuzzer), `-DWR_WITH_OPENSSL=OFF`, `-DWR_BUILD_HOST=OFF`. Warnings are errors by default and must stay so.

Useful ctest selections: `ctest -L util` (one module's tests: the label is the first word of the name), `ctest -R core` (the mechanical gates and the footprint test), `ctest -L fuzz` (seed replays), `ctest -R client.pump -V` (one test, verbose).

### The four CI flavours

[.github/workflows/harness.yml](../.github/workflows/harness.yml) builds and tests:

| Flavour | Configure |
|---|---|
| gcc | `-DCMAKE_C_COMPILER=gcc` |
| clang | `-DCMAKE_C_COMPILER=clang` |
| clang + ASan + UBSan (gcc too) | `-DWR_SANITIZE=address,undefined`; the `core_no_libc` / `core_no_globals` checks are not registered here because the sanitizer runtime adds symbols |
| 32-bit and iPXE flags, compile only | `cmake --build build/harness --target wr_core_m32` (gcc and clang) and `--target wr_core_ipxe_flags` (gcc) |

The workflow `.github/workflows/core.yml` builds and tests the plain command (`cmake -S harness -B build && cmake --build build && ctest --test-dir build`, lab tests excluded) from a clean checkout with gcc and clang in Debug, Release and MinSizeRel; `.github/workflows/harness.yml` repeats the Debug build with the sanitizers and carries the jobs below; `.github/workflows/vectors.yml` re-checks the public vectors, including those of part C (`check_osdc.py` and `check_imgio.py`, their self-tests that must see every damaged copy rejected), with python3 alone.

Also in CI: `object-gates` (the no-libc and no-globals checks on optimised builds, Release and MinSizeRel with gcc and clang, because the Debug test builds never show what an optimiser turns a loop into), the same two checks on the 32-bit and iPXE-flag objects, `static-limits` (`tests/ci-docs-hardening/check_callgraph.py`: no recursion, no frame of unbounded size, at most 17 frames (14 before part D) and 3,328 bytes of stack along any call chain of the core, and a budget of its own for each entry point of part B (map placement, store step, full-map decode, incremental apply, CRUSH decode, rule interpreter) and of part C (the OSD step `wri_osdc_step`, the engine's OSD stage `wri_client_osd_begin`, the image step `wri_rbd_step`, the request encode `wri_mosdop_encode`, the reply decode `wri_mosdopreply_decode`, and the reply path through the msgr2 upper-layer table, which gcc's graph cannot follow and `--link` adds) and of part D (the secure receive step `wri_m2s_rx_step`, the secure transmit frame `wri_m2s_tx_frame` and the GCM update chain `wri_pgcm_update` with the rest of the chains of design 36.4, budgets about 8 % above the larger of the stack measured with gcc 13 and gcc 15); the `--entry` arguments are read from the workflow by the ctests `map.hardening` and `secure.hardening`, so the tests and the job cannot drift apart), the constant-time checks under Valgrind (a required step: a runner without Valgrind fails the job), the libFuzzer smoke run described below, and `ipxe-gates` (the only job that checks out `third_party/ipxe`, with `WRT_IPXE_REQUIRE=1` so a gate that could not run is a red job: the core against iPXE's headers and flags, `-std=gnu17` and `-std=gnu2x`, `ipxe/tools/build.sh check`, the call-graph budgets with `-Os` and `-m32 -Os`, and the self-test of the gates; section "Gates for the iPXE build" below). The sanitizer runs set `ASAN_OPTIONS` / `UBSAN_OPTIONS` so a finding fails the test. The `ipxe` workflow (`.github/workflows/ipxe.yml`) is the other half: it builds the iPXE targets from a clean submodule plus `ipxe/patches`.

The jobs of `harness.yml` run on both images, `ubuntu-24.04` (gcc 13.3, clang 18.1, the one the measured stack numbers of the docs come from) and `ubuntu-26.04` (gcc 15.2 and clang 21.1.8, which warns about things the older compilers do not: the CI fix `43ef100` was one of them, and the 1,048-byte frames of the map half under clang 21 with the sanitizers another); the workflow file core.yml follows `ubuntu-latest`, the 26.04 image. Both the sanitizer build and the libFuzzer smoke run therefore exist on the newest compilers in CI, not only on the lab box. `tools/ci26_vm.sh` makes the same 26.04 toolchain on the lab box (a KVM guest under one directory, no root, no bridge; `selftest` needs no VM and is the ctest `ci26.selftest`) and `ci26_vm.sh run TREE` repeats the matrix of both workflows there: the four flavours plus Release and MinSizeRel, plain and with the sanitizers (`-f all`), `-Werror`, a build that prints any `warning:` counts as failed, then the 32-bit core, the iPXE-flag core, the header check and the object gates. Run it, and the same matrix on the 24.04 lab VM, before a change lands; the call-graph budgets and the libFuzzer smoke run stay CI-only (run `check_callgraph.py` and `fuzz_long.sh` by hand).

The core compares bytes with `wri_ct_memeq` and never calls `memcmp`, so clang at -O2 has no `memcmp(...) == 0` to turn into `bcmp`; no compiler flag is needed for `core_no_libc` on an optimised clang build (the CI jobs that pass `-DCMAKE_C_FLAGS=-fno-builtin-memcmp` still do, harmlessly).

## Tests

One executable per `test/test_<module>_<what>.c`, registered as ctest `<module>.<what>` with label `<module>` (`test_util_mem.c` is `util.mem`, `test_core_budgets.c` is `core.budgets`). A test that needs OpenSSL ends in `_ossl`. Exit code 77 is a skip with a printed reason; a skip never hides a failure.

- `test/support/`: the tiny framework (`wrt.h`: `WRT_CHECK`, `WRT_CHECK_U64`, `WRT_CHECK_STATUS`, `WRT_CHECK_MEM`), a JSON and hex reader so tests read `vectors/**/*.json` in place, and the **simulators**: `sim_m2` (a scriptable msgr2 server with fault hooks) and `sim_mon` (a fake monitor on top of it, with the cephx server side for both key types, `MMonMap`, `MOSDMap` from the committed vectors, renewal and restart). They are written from the spec notes, not from the client code.
- `core.budgets` (`test_core_budgets.c`) prints the footprint of the three profiles and the high-water mark of every pool and buffer after a full session (login, a map message of three quarters of the profile's cap, a pushed epoch, a monitor restart and recovery) and fails if a product profile exceeds its documented budget (`test/core_budgets.h`), an announced size is not what the engine took, or a buffer ever ran over its capacity. The engine gets regions of exactly the announced size, pre-filled with a byte pattern and surrounded by guard bands: a write outside them fails the test, and after destroy the whole arena must be zero. A second run per product profile sends a map message above `mon_msg_cap` and checks that it is dropped, the session survives and nothing outside the regions is touched. Run `ctest -R core.budgets -V` to see the table.
- `core.docs` (`test_core_docs.c`) checks the documents against the tree: the footprint table of `core/README.md` against `wr_client_mem_required`, the 500-line limit of the core files, a committed seed and a README entry for every fuzz target (an empty seed directory would pass the replay without running anything), every test name the READMEs mention, the SPDX tag of every product file, and that the CI workflow keeps warnings as errors and never ignores a failure.
- `client.mem` checks the exactness of `wr_client_mem_required` at every base alignment; `client.pump` drives the engine through the public pump API with a small in-test host.
- Client glue of part C (the OSD client and the image layer inside the engine, module client-glue-osd), all through the public API against a simulated monitor and simulated OSDs over one object store (`test/client_osd_rig.h` plays the host): `client.osd.open` (open, I/O against a flat model and the store, data pool, two images, close, more OSDs than sessions, monitor and OSD restarts with held answers, a map change, destroy mid-I/O), `client.osd.api` (every status of `wr_image.h` in the header's order, stale handles), `client.osd.mem` (the memory plan is exact for the profiles and random configurations, every refused configuration), `client.osd.events` (image events, the stall and the resume, a fatal engine, the event ring under a burst, a key canary over whole sessions), `client.osd.clock` (a submit or an open after a quiet period is timed from the next run, not from the old clock), `client.osd.geom` (object names and offsets for images up to 16 TiB, partial last objects, orders 12 to 25, missing objects read as zeros) and `client.osd.link` (the connection-table hooks of the session layer called directly: gates, slots, wiping).
- Part B (OSD map, CRUSH, placement): `map.vec.full` / `map.vec.pgs` / `map.vec.place` / `map.vec.err` run the committed lab vectors (`vectors/osdmap`, `vectors/crush`, `vectors/public/mapb`) through the real decoders and the real pipeline; `osdmap.budget` and `mapstore.mem` generate clusters of 100 to 8,192 OSDs and print the real per-OSD costs (see [core/README.md](../core/README.md), memory footprint); `oracle.cli` tests the comparison tool `oracle/wr-maporacle`, and a second ctest runs `tools/map_oracle_lab.sh --selftest` (every committed vector through the tool and the comparison code, plus negative tests), both without a cluster.
- `place.live` (`test_place_live.c`) replays `vectors/public/placement`: the full map and the 102 incrementals that the monitor sent to the client over a real session (CRCs verified), applied by the real incremental path, and at **every epoch** the PG tables of the tracked pools against the digest of `osdmaptool`'s table of that epoch; at each of the 23 states the whole PG table column by column, the held map against `ceph osd dump`, every one of 2,000 object names in every pool through hash, PG and CRUSH against the monitor's `ceph osd map` answers, and the monitor's own full maps and the full map the client was sent after a missed incremental against the chain. `vectors_placement_check` checks the files (hashes, contiguous chain, no stray file, no key-looking text). How the vectors were made and what they cover: [vectors/public/placement/README.md](vectors/public/placement/README.md).
- `map.hardening` (`test_map_hardening.c`) keeps the part B hardening wired in: the five fuzz targets exist and have seeds, the CI smoke job and `tools/fuzz_long.sh` name them, both READMEs list them, no committed seed of them is larger than the 64 KiB input cap of the fuzz runs (libFuzzer would cut it), the workflow still passes the global limits (14 frames, 3,328 bytes) and a budget for each of the six part B entry points, and the call-graph check passes with exactly the `--entry` budgets the workflow passes (it compiles the core with gcc and needs python3; without them that part is skipped, with a message).
- `osd.hardening` (`test_osd_hardening.c`) is the sibling of `map.hardening` for part C: the seven fuzz targets of milestones 6 to 8 (`fuzz_osd_reply`, `fuzz_osd_backoff`, `fuzz_rbd_cls`, `fuzz_osd_sess`, `fuzz_osd_req`, `fuzz_rbd_open`, `fuzz_client_osd`) exist with committed seeds below the 64 KiB input cap, the CI smoke job and the `partc` preset of `tools/fuzz_long.sh` name exactly them, both READMEs list them and every part C test group (`osd.*`, `rbd.*`, `client.osd.*`); the part C stack budgets are in the workflow (`wri_osdc_step`, `wri_client_osd_begin`, `wri_rbd_step`, `wri_mosdop_encode`, `wri_mosdopreply_decode` as `--entry` budgets, which `map.hardening` runs with the rest, and the reply path through the msgr2 upper-layer table as `--link` and `--entry=` tokens that this test reads out of the workflow and runs: a budget of 1 byte must fail with status 1 and a link or an entry that is not in the graph must be a tool error, status 2); `tools/osd_fault_lab.sh` parses, creates and removes only `wrtest-ofl-*` images, restores the daemons, the `in` state and the upmap entries it added, and contains no command that destroys cluster state; and the design document has section 31.3 with a line for every open item R-C1 to R-C12 and Q12 to Q20, and the roadmap shows milestones 6 to 8 as done. It compiles the core with gcc and needs python3; without them the call-graph part is skipped, with a message.
- `imgio.replay` (`test_imgio_replay.c`), `vectors_imgio_check` and `vectors_imgio_selftest` (module vectors-d): the captures of the core's OWN image I/O against a real OSD in `vectors/public/imgio` (three scripted `wr-rbd` sessions: a writer on an empty image of 4 KiB objects, a writer on an image with two snapshots, a reader on a default-feature image; the requests the core sent, the real OSD's replies, the stock `rbd export` of each image before and after; see [vectors/public/imgio/README.md](vectors/public/imgio/README.md)). `imgio.replay` re-encodes every captured request byte for byte, runs the same scripts through the whole engine against the simulated monitor and OSDs and compares request by request and answer by answer with the real OSD (the same objects, operations, offsets, lengths, flags, snapshot context and payload sizes; the same result and output length of every operation), then the content with the export. `vectors_imgio_check` is the independent python checker (`scripts/check_imgio.py`: everything `check_osdc.py` checks plus the image level: object names, the snapshot context, the payload against the script's patterns, a model of the objects replayed over the requests against every read reply and the export); `vectors_imgio_selftest` feeds it 12 damaged copies. All three skip with a reason when the directory is absent.
- Constant-time crypto of part D (design 35, `core/src/crypto/`): `crypto.aesct` (the bitsliced AES against the table-driven reference and the published FIPS 197 and SP 800-38A answers, the S-box in every lane, 100,000 random cases in and out of place, `ctr32` at the counter wrap) and `crypto.aesct.ossl` (the same against OpenSSL), `crypto.ghash` (eight GCM specification cases, a bit-by-bit multiplication written in the test on 200,000 random cases and all single-bit pairs, the algebra), `crypto.gcm` (every case of `vectors/secure/gcm-nist.json`, a million random split points against the independent reference `test/support/ref_gcm.c`, every single-bit change refused, the state errors, the length limit, partial overlap refused) and `crypto.gcm.ossl`, `crypto.pgcm` (the per-direction dispatcher with a fake host table that counts calls and records every breach of the contract of `wr_host.h`), `ref.gcm` and `ref.gcm.ossl` (the reference itself, checked against FIPS 197, the 18 specification cases, the CAVP cases and OpenSSL, so that it can be the oracle of everything else). `crypto.ct.*` is the constant-time evidence without timing: `crypto.ct.vg` runs the primitives with key, IV and data marked undefined under Valgrind (ctgrind) and, in process, against the reference; the checks around it that CMake registers by name (crypto.ct.valgrind: the drive under Valgrind with a known-bad control, a table AES and an early-exit compare, that Memcheck must report; crypto.ct.rodata and crypto.ct.rodata.selftest: no read-only or initialised data section of 256 bytes or more in the four constant-time objects, and a scan proven able to see a lone S-box) skip with a reason when Valgrind or binutils are missing, unless `WRT_CT_REQUIRE=1` (CI sets it) makes that a failure.
- Secure mode of part D: `m2.modes` (the offer table of design 34.2, every policy by peer type), `m2.sec.init` / `m2.sec.len` / `m2.sec.nonce` / `m2.sec.switch` (the slices of the connection secret proved on the wire against the independent reference, the wire arithmetic of a frame, the nonce stream and its limit and wrap, the switch at a frame boundary), `m2.sec.tx.frames` / `m2.sec.tx.stream` / `m2.sec.tx.diff` and `m2.sec.rx.frames` / `m2.sec.rx.bad` / `m2.sec.rx.budget` (the transmit and the receive codec: every frame shape, every delivery pattern, every damaged byte refused, the work budget, the direct window, differential against the simulator's independent encoder), `m2.sec.replay` (the real receive parser and the real transmit on the core's own secure sessions captured against the real cluster, `vectors/public/secure`; every kind of byte of every recorded frame damaged one bit at a time), `m2.conn.sec.hs` / `m2.conn.sec.msgs` / `m2.conn.sec.fail` (a whole connection: the handshake in both modes, messages both ways, every failure path ends the connection and counts), `auth.secret` (the connection secret carried by the cephx replies), `sim.sec`, `sim.sec.hs`, `sim.sec.mode` and `sim.sec.fault` (the simulator's secure peer, which is the test of the tests), `client.sec.mem` / `client.sec.conn` / `client.sec.events` (the engine under every policy x allowed-modes combination: the memory plan is exact, a refusal never becomes a silent crc, the counters, the log record), `host.gcm.aesni` (the AES-NI and PCLMULQDQ hook: gating on each CPUID bit, NIST answers, differential against the reference, interleaved states, the counter near the wrap, key objects wiped), `host.loop.sec` and `host.tool.rbd.sec` (the Linux host and the `wr-rbd` tool against pthread peers that speak secure mode, with and without the hook; they use the slow independent GCM of the simulators, so their limits leave a factor of three: the Debug builds with the sanitizers take 5 to 7 minutes each on a fast machine) and `secure.skel` (the frozen interfaces and constants of the part D skeleton). `vectors_secure_check` and `vectors_secure_selftest` are the independent python checks of the captured secure sessions (the cephx exchange replayed from the handshake bytes, every frame encrypted again and decrypted with a library; 31 damaged copies refused).
- The comparison with krbd (design 33): `host.cmp` (every phase and direction of the engine `host/wrl_cmp.c` against the simulated cluster with an in-process device), `host.cmp.edges` (the edge generator, no network), `host.tool.krbdcmp` (the built tool `wr-krbdcmp` over real sockets with a regular file as the device) and `krbdcmp.selftest` (`lab/krbd-compare.sh --selftest` against stand-in `rbd` / `ceph`: an injected failing step must still unmap, remove the images and match the state snapshot). `lab.secure` (label `lab`) is the live secure matrix of `lab/secure-live.sh` (forces the lab cluster to secure and to crc one daemon at a time, restores it; the test bounds the script and puts the lab back); `secure.live.dry` and `securelive.selftest` run the same script against stand-in cluster tools, with a failure injected at every step: the run must fail and the restore must still run.
- `secure.hardening` (`test_secure_hardening.c`) is the sibling of `map.hardening` and `osd.hardening` for part D: the five fuzz targets of secure mode (`fuzz_gcm`, `fuzz_m2_sec_tx`, `fuzz_m2_sec_rx`, `fuzz_m2_conn_sec`, `fuzz_client_secure`) exist with committed seeds below the 64 KiB input cap (and `fuzz_cx_reply` keeps its secret-carrying seeds), the CI smoke job has a step that loops over exactly these names and the `partd` preset of `tools/fuzz_long.sh` lists exactly them, both READMEs list them and every part D test group; the options of `fuzz_long.sh` that are refused (`-w 0`, `-w x`, a bad preset, `-t` with `-p`) are refused with status 2 before anything is built; the part D stack budgets are in the workflow as `--entry NAME=BYTES` (the secure receive step, the secure transmit frame, the GCM update chain and nine neighbours), read out of the workflow and run (a budget of 1 byte must fail with status 1, an entry that is not in the graph is a tool error, status 2; the global limits of the two measuring steps must be the same numbers); the Valgrind step is a required step of the workflow; every file of the part D modules is in `core/sources.txt`; the licence and copying scan (no crypto library and no kernel client named anywhere in `core/`; no authorship trailer or tool vendor named in any text file of the repository; no AES substitution table in the four constant-time files); and the design document has section 41.3 with a line for every open item R-D1 to R-D9 and Q-D1 to Q-D7, the roadmap shows milestones 9 and 11 as done, with the numbers of the lab runs that showed it, and Phase 1 as not closed until the exit run with the faults has reported, in both languages, and the secure-mode note carries the lab's answers to its questions 6.4 and 6.5. It compiles the core with gcc and needs python3; without them the call-graph part is skipped, with a message.
- Phase 2 modules (core/src/handoff, rburl, ra; all pure, no network): `handoff` (the byte layout field by field against the design document, round trips, the encoder as a pure function, the 1,024-byte cap, every refusal, truncation at every length and single flipped bits), `handoff.vec` (the golden vectors of `vectors/handoff/handoff-v1.json`, written by the independent Python implementation `gen_handoff_vectors.py`; `handoff.vectors_in_sync` fails when that file and the script disagree), `rburl` (defaults, every option, every refusal with its own status and place, the length caps, the password, the key text, no secret left behind), `ra` (configuration, every line transition, hit / wait / miss, the stream detector, the window planner, lines beyond 2^32) and `ra.sim` (the cache driven the way the iPXE block device will drive it, against the whole engine, with writes, cancelled and timed-out prefetches, a reopen and a full request table).
- Gates for the iPXE build, in ctest (module harness-gates; the scripts compile the core themselves, so the expensive ones are registered once, in the plain gcc flavours): `ipxe.check` (`ipxe/tools/build.sh check`), `core_std_c` (every core file as `-std=gnu17` and `-std=gnu2x`, freestanding, iPXE's warning set; iPXE sets no `-std` and gcc 15 gives it C23), `core_ipxe_headers_i386` / `core_ipxe_headers_x86_64` (every core file against iPXE's own headers and flags and the shim `ipxe/src/rbd_core_cfg.h`: iPXE's `<stdint.h>` has no `uintptr_t` and none of the limit macros; then the undefined symbols of the objects, which must all be ones iPXE defines out of line; skipped, exit 77, without `third_party/ipxe`, and a failure with `WRT_IPXE_REQUIRE=1`), `core_callgraph_i386` / `core_callgraph_x86_64` (`tests/ci-docs-hardening/callgraph_ipxe.sh`: the call-graph limits and a budget for each glue-facing entry point with `-Os`, and `-m32 -Os` for the BIOS images; every core function the glue calls must have a budget) and `gates.selftest` (each gate is fed a copy of the core or of the shim with one seeded violation and must reject it for the stated reason, and accept the copy without it).
- `lab.mon` and `lab.map` (label `lab`) run the client against the real lab monitor and are skipped without `WR_LAB_*` in the environment. `lab.map` is the map-enabled client: it logs in with each key type, tracks pools, takes the monitor's maps, optionally keeps following the cluster for `WR_LAB_FOLLOW_S` seconds while another shell changes it, checks that every placement is a consistent target and that not one map entry failed to decode, and can write the placements to `WR_LAB_OUT` for a script to compare with `ceph osd map` (the header of the test says how).

## Fuzzing

`fuzz/fuzz_<target>.c` defines `LLVMFuzzerTestOneInput`. Without `WR_FUZZ` each target is linked with `fuzz_replay_main.c` and ctest replays every file in `fuzz/seeds/<target>/` (`fuzzseed.<target>`), so the committed corpus is a regression test on every run. Targets: `util_cursor`, `denc_addr`, `m2_rx`, `m2_ctl`, `m2_conn`, `cx_envelope`, `cx_reply`, `mon_msgs`, `mon_session`, `client_session`, and `smoke`; and for part B (OSD map, CRUSH, placement, `docs/design/core-architecture.md` section 18) `crush_dec`, `crush_map`, `osdmap_full`, `osdmap_inc` and `mapstore`; and for part C (OSD sessions, RBD, block I/O, section 30.1) `osd_reply`, `osd_backoff`, `rbd_cls`, `osd_sess`, `osd_req`, `rbd_open` and `client_osd`; and for part D (secure mode, section 39.4) `gcm`, `m2_sec_tx`, `m2_sec_rx`, `m2_conn_sec` and `client_secure` (`cx_reply` also gained seeds that carry a connection secret). `fuzz_crush_dec` decodes a CRUSH blob into a room between guard bands twice with different pre-fills (identical output, nothing written outside, a decoded region survives `wri_crush_check` and every accessor walk, a damaged region is judged without a crash); `fuzz_crush_map` runs the audit and the rule interpreter over a blob, a rule, an `x`, a weight array and a work budget (bounded work, results inside the map, a pure function of the inputs, an audited map never fails for a structural reason); `fuzz_osdmap_full` and `fuzz_osdmap_inc` decode a full map and apply an incremental to the lab's epoch-42 map (the same two pre-fills, the exact-size slot gives the same map and one byte less is `WR_E_MAP_BUDGET`, the held map is never written, an applied incremental does not apply twice); `fuzz_mapstore` feeds the map store the front of an `MOSDMap` message under a scripted clock (the epoch never goes down, an incremental is applied only to the epoch before it, every failure leaves a full-map request pending, nothing reads a front after its release, every placement answer is of the documented set). Every crasher is minimised and committed under `seeds/`.

`fuzz_client_session` is the whole-engine target. After a real handshake with the simulated monitor, the input script decides where the world misbehaves: bits flipped in the monitor's stream, connections cut, a monitor restart, a clock that steps back, a failing random source, calls that break the host contract, and two ways of playing the monitor itself: a well-framed `MESSAGE` with fuzzed type, header version and front (valid CRCs, so the message decoders are reached), and raw bytes that replace the stream. It asserts: no crash or undefined behaviour, the pump settles, pool accounting stays inside the configuration, the engine recovers when the world is good again, nothing is written outside the first `arena_used` / `bulk_used` bytes of the two pattern-filled regions (guard bands and a spare tail are checked), and the footprint equals what `wr_client_mem_required` announced. Every input is played twice with the two regions pre-filled with different byte patterns, and a digest of everything the host can observe (transmitted bytes, events, actions, map messages, the state after each pump) must be identical, so a decision taken on a byte the engine never wrote (an uninitialised read) shows up as a divergence.

The target `client_osd` (`fuzz_client_osd`) is the same idea with the OSD client and an RBD image on the engine (module client-glue-osd, `docs/design/core-architecture.md` section 27): the whole engine runs against the simulated monitor and up to three simulated OSDs over one object store, an image of 1 MiB is opened for writing, and the input script is a series of host calls (writes, reads, flushes, discards, write-zeroes, cancels, reopens, a clock that moves without a run), faults (OSD and monitor restarts, silent or lying OSDs, held and dropped answers, EAGAIN, redirects, refused authorizers) and hostile bytes (well-framed messages of any type on a connection that finished its real handshake, raw bytes, flipped bits). It asserts that a request completes at most once and, in a world the fuzzer did not corrupt, exactly once; that a READ that succeeds returns what a flat model of the image says; that the pools stay inside the configuration; that the footprint is what `wr_client_mem_required` announced; and, by playing every input twice on differently pre-filled regions, that nothing the host can observe depends on a byte the engine never wrote.

The six decoder and module targets of part C (design section 30.1; each input is an exact-size heap copy, so ASan sees any over-read, and a violated property traps): `fuzz_osd_reply` (byte 0 picks the MOSDOpReply front decoder, the SPARSE_READ output decoder or the STAT output decoder; success means the structural rules of the note hold, failure leaves the output zero), `fuzz_osd_backoff` (the MOSDBackoff decoder, the object-position comparison and the acknowledgement encoder, whose output must decode again), `fuzz_rbd_cls` (the RBD class-call decoders and encoders and the refusal rules of the image profile; every decoder consumes its payload exactly or fails with cleared outputs, and an accepted snapshot context passes `wri_snapc_valid`), `fuzz_osd_sess` (hostile frames delivered to READY OSD sessions through the upper-layer callbacks the way the msgr2 connection calls them, mixed with everything the engine does to the table: acquire, ready, lost, time, resets, sends, stale callbacks; the table never writes into a data sink, never writes the front buffer beyond its cap, and every live entry has its own connection slot), `fuzz_osd_req` (a program of submits, cancels, map changes, time, connection events and hostile replies and backoffs against the real request engine on the real session table: slots are conserved, tids are never reused, a sink is only handed out for an operation that is SENT on that session, no message goes out into a standing backoff or for an operation that is not about to be sent, an operation completes once, and after every fault is lifted the table is empty) and `fuzz_rbd_open` (hostile answers to the control reads of the open and refresh machine against the real image layer: an OPEN image came through the profile, with a valid snapshot context of at most `max_snaps` ids; no control slot is ever lost; the first failure of an image is never replaced).

The five targets of part D (design 39.4; each asserts that nothing is written outside the sinks and the bounce buffer, that a success means the structure rules held and the sinks hold exactly the plaintext, that a tag corruption is never accepted, that the same input with differently pre-filled regions behaves identically, and that no secret, key or nonce byte reaches an errinfo or a log record): `fuzz_gcm` (random operation scripts, key sizes, split points and corruptions, differential against the reference `ref_gcm`, through the portable code and through the dispatcher with a fake host table), `fuzz_m2_sec_tx` (random frame shapes, consume and bounce sizes, each wire stream decoded by the independent reference and the plaintext compared), `fuzz_m2_sec_rx` (encrypt-then-parse with deliberate corruptions: every delivery pattern, a work budget, a tag damaged anywhere), `fuzz_m2_conn_sec` (a whole secure connection against the simulator with fuzz-driven faults: refusals, cut streams, damaged frames, a lost key) and `fuzz_client_secure` (the whole client under a secure policy against the simulated monitor and OSDs, fuzz-driven simulator faults). Their committed seeds are the frames of the public secure captures, the synthetic vectors and the inputs the module runs kept.

The two targets of Phase 2 (each input is an exact-size heap copy; a violated property traps). `fuzz_handoff`: byte 0 picks the mode, the rest is the payload: a body (decode, and on success the encoder writes the same bytes back, since the decoder takes one canonical form only), a whole ACPI table (`wr_handoff_decode_table`), a body wrapped in a valid ACPI header so the fuzzer reaches the body parser through the table entry point, or a description (encode gives a defined status, writes nothing on a refusal, gives the same bytes twice, and the result decodes to the same description). `fuzz_rburl`: byte 0 is a set of flags (which of the user, authority, path, query and setting texts are absent, a real key instead of field 6, a password in the URL), the rest is cut into the six texts of a `wr_rburl_in`; the status must be one of the known set, a failure leaves the spec zero and an errinfo that points inside the query, the result must be a function of the input only (the same input with the spec pre-filled with other bytes gives bit-identical results), and a success survives a round trip through a canonical URL; a second mode compares the percent decoder with an independent one. Seeds: `fuzz/seeds/fuzz_handoff` and `fuzz/seeds/fuzz_rburl`.

To fuzz for real (clang, libFuzzer), instrument the core as well as the target. `WR_FUZZ=ON` alone instruments only the target file, so the fuzzer would see no coverage of the code under test; the global flag below fixes that:

```sh
CC=clang cmake -S harness -B build/fuzz -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
    -DCMAKE_C_FLAGS=-fsanitize=fuzzer-no-link -DWR_FUZZ=ON -DWR_SANITIZE=address,undefined
cmake --build build/fuzz
mkdir -p /tmp/corpus && cp harness/fuzz/seeds/fuzz_client_session/* /tmp/corpus/
build/fuzz/fuzz_client_session -max_total_time=60 -max_len=4096 /tmp/corpus
```

`tools/fuzz_long.sh` does the same for every target at once (`sh harness/tools/fuzz_long.sh -s 900 -j 4`, optionally `-m` to minimise the corpora against the committed seeds afterwards and print how many inputs add coverage; `-t "fuzz_m2_rx fuzz_cx_reply"` picks targets, `-p partb` picks the five targets of part B, `-p partc` the seven of part C and `-p partd` the five of part D (not together with `-t`), `-w N` runs every target with `N` libFuzzer worker processes (`-fork=N`; the cores in use are the `-j` value times `N`, so keep that at or below the idle cores of the machine: `-j 3 -w 8` is 24), and a name that was not built, a failed build or an empty target list is an error, not a shorter run). The last long run of part A (15 minutes per target, then 10 to 15 minutes again after the last core change) did about 677 million executions with no crash and no sanitizer report. The long run of part B (16 minutes per target, the five targets side by side on the 8-core lab VM, ASan and UBSan, the core instrumented) did 18.6 million executions with no crash, no timeout, no out-of-memory and no sanitizer report; numbers per target are in the hardening section of [core/README.md](../core/README.md). The committed seeds are the vectors, the public captures cut into frames and payloads, the `mapgen` output and single-field mutations of the maps, and the coverage-adding inputs of those runs (1,478 inputs for the part B targets, 3.1 MB, from the minimised corpora; they derive from the scrubbed vectors only). CI runs every target for 30 s on a copy of its seeds, and fails if a part B target was not built or has no seeds. The long run of part C (`tools/fuzz_long.sh -p partc -s 960 -j 4 -m`: 16 minutes per target, four side by side, ASan and UBSan, the core instrumented) did 390 million executions with no crash in the core and no sanitizer report; the run found one defect in the target `fuzz_osd_req` itself (its scripted map can go back, its final emptiness check did not allow for it), fixed, with its input committed as a regression seed (`regress_map_epoch_goes_back.bin`); the numbers per target are in the part C hardening section of [core/README.md](../core/README.md). The final-hardening pass of part C ran the targets again (11 minutes per target, then again after a fix): `fuzz_client_osd` found, after 2,220 executions, a livelock in the OSD session table (the cool-down slot of a failed OSD was reused for another OSD, so with fewer sessions than OSDs in use and one OSD refusing connections the engine redialled it at every pass without time passing; `regress_cooldown_slot_taken.bin`, 18 bytes, is its regression seed; design section 31.4); the fixed tree ran the four affected targets again without a finding. The 3,622 inputs of the first run that add coverage, and the roughly 3,000 of each later one, are not committed. CI runs every target for 30 s and fails if a part C target was not built or has no seeds. The duration for the Phase 1 exit criterion (60 s per target on every push, 1 h nightly, 8 CPU-hours per target before milestone 10 closes) is the maintainer's decision.

## Gates for the iPXE build

The core is built into iPXE through a thin shim, and iPXE is not a hosted C environment: its `<stdint.h>` has the fixed-width types and nothing else (no `uintptr_t`, none of the limit macros `UINT32_MAX`, `INT64_MIN`, `SIZE_MAX` that the core uses), its `memmove` is an inline wrapper with no symbol, it sets no `-std` (gcc 15 therefore compiles it as C23), its BIOS images are 32-bit and its stack is small. These gates are what lets a core change be judged against that in ctest, before an iPXE build is started. They are independent of the flags of the tree they run from (each script compiles the core itself).

| Gate (ctest) | Script | Fails when |
|---|---|---|
| `core_ipxe_headers_x86_64`, `core_ipxe_headers_i386` | `tools/check_ipxe_headers.sh` | a core file does not compile against the headers of the pinned iPXE tree (`-nostdinc`, iPXE's include path, `-include include/compiler.h`, `-ffreestanding -Os`, `-Wall -W -Wformat-nonliteral -Wshift-overflow=2 ... -Werror`, no `-std`, the architecture flags of iPXE, for x86_64 the EFI image's `-fpie -mno-red-zone`, the shim `ipxe/src/rbd_core_cfg.h` as the host configuration header): a macro or type the shim does not supply, a function iPXE's headers declare differently, a warning iPXE would stop at; and then, from the objects it keeps, a symbol that no core object defines and iPXE does not define out of line (on x86 only `__memcpy`, `__memcpy_reverse`, `__memmove`, `memcmp` and the 64-bit division helpers exist: a call to `memcpy`, `memmove` or `memset` (a `__builtin_memmove` with a variable length, or whatever the optimiser expands into one) is an undefined reference at the iPXE link, and a compile-only check cannot see it); and any writable global (`.data`, `.bss`, common) in those objects, which the harness's own `core_no_globals` would not see on objects built with the shim (iPXE's own one-byte `__debug_disable_<object>` is the one allowed). Only gcc judges (iPXE's headers are not clang-clean, so with clang the script skips). Skips (77) without `third_party/ipxe`; `WRT_IPXE_REQUIRE=1` makes a skip a failure |
| `core_std_c` | `tools/check_core_std.sh` | a core file does not compile as `-std=gnu17` or `-std=gnu2x` with the iPXE warning set (C23 keywords such as `bool`, `true`, `nullptr`, `constexpr` used as names; an empty parameter list called with arguments) |
| `core_callgraph_i386`, `core_callgraph_x86_64` | `tests/ci-docs-hardening/callgraph_ipxe.sh` (runs `check_callgraph.py --cflag=-m32 --cflag=-Os` / `--cflag=-Os`) | a recursion, more than 19 frames, more stack than the global limit (i386 2,880 bytes, x86_64 3,216; measured 2,632 and 2,944) or than the budget of one of the 59 glue-facing entry points (`wr_client_*`, `wr_config_*`, `wr_conn_*`, `wr_image_*`, `wr_handoff_*`, `wr_rburl_*`, `wr_ra_*`, the key and monitor-list parsers, the status texts), or a core function that a C file of `ipxe/src` calls and that has no budget (`--glue`: the table must be every entry point the glue calls, not the ones the design listed), or an entry point that was renamed away or that the core only calls and never defines (a tool error, not a pass). The i386 run skips (77) when the compiler has no 32-bit system headers (`gcc-multilib`), a failure with `WRT_IPXE_REQUIRE=1` |
| `ipxe.check` | `ipxe/tools/build.sh check` | a glue file or self-test lacks its licence or Secure Boot line, a patch has wrong hunk counts, a name collides |
| `gates.selftest` | `tests/ci-docs-hardening/gates_selftest.py` | any of the above fails to reject a seeded violation (a deepened chain, a frame over an entry budget, a renamed entry point, an entry the core does not define, a glue call with no budget, a core file using `INT16_MAX`, one that needs `abort()`, one that ends in a `memmove` call, a shim without `uintptr_t` or one of its macros, a variable called `true`) or rejects the copy without it |

`check_callgraph.py` gained `--cflag FLAG` (extra compiler flags, so `-m32` and `-Os` can be measured), `--core DIR` (measure another copy of the core; the self-test feeds it copies with a deepened chain) and `--glue DIR` (every core function that the C files below DIR call must be an `--entry`; comments and string literals do not count), refuses an `--entry` that the core does not define (it would measure 0 bytes for ever), and compiles the files in parallel. The `static-limits` job and its numbers (`-O2`, x86_64) are unchanged. Budgets are the largest of gcc 11, 13, 14 and 15 plus 8 %, rounded up to 8 bytes and at least 16 bytes above the measurement; the table and how it was set are in `callgraph_ipxe.sh`. The measurement leaves out `-mregparm=3`, which iPXE adds for i386 and which makes frames smaller, so it is the conservative number.

## Rules for test and harness code

Harness code may use libc; it never ships. It follows the same warning policy as the core minus the few warnings that fight with libc helpers. No secrets in the repository: lab keyrings are read from a path in the environment, copied to the VM only into a `0600` file outside the repository, and never printed. Tests never run destructive commands on a cluster.

**状态:Phase 1 里程碑 1 到 8 的构建、单元测试、模拟器、fuzz 目标和 CI 工作流都可用,里程碑 10 的解码器部分也覆盖了 OSD map、CRUSH、定位以及对象读写一半(OSD 消息、会话、请求引擎、RBD 打开与块读写)。** 171 个 ctest 用例(不含会跳过的三个 lab 用例共 168 个):各核心模块(含 OSD map、CRUSH、定位和 map 存储)的单元测试、抓包回放、实验集群 map 向量的测试(`map.vec.*`、`vectors_mapb_check`)、比对工具(`oracle.cli` 与比对脚本的自检)、实时定位证明的向量回放(`place.live`、`vectors_placement_check`)、机械检查(无 libc、无全局变量、freestanding 链接)、内存预算测试、文档核对、第二部分的加固检查(`map.hardening`),以及每个 fuzz 目标的种子回放。`tools/fuzz_long.sh` 可对全部目标做长时间 fuzz(`-p partb` 只跑 map 相关的五个目标);第一部分最近一轮约 6.8 亿次执行,第二部分(五个目标各 16 分钟,ASan + UBSan)约 1860 万次执行,均无崩溃、无 sanitizer 报告。`tools/map_oracle_lab.sh` 在实验集群的虚拟机里把核心的 map、CRUSH 和定位结果与 Ceph 自己的工具逐项比对(最近一轮 132,358 次比较,0 处差异)。`tools/map_placement_lab.py` 让完整客户端 `winrbd-mapwatch` 通过真实 monitor 会话跟随实验集群,同时用管理命令改动集群(upmap、upmap primary、pg_temp、primary_temp、亲和度、reweight、out、拆分、删池、漏掉一个增量、断开连接),逐项与 `ceph osd map`、`osdmaptool`、`ceph osd dump` 比对(212,000 个对象定位、103 个 epoch 的 28,510 行 PG,0 处差异,集群已还原);向量在 `vectors/public/placement`,由 `place.live` 离线回放。需要实验集群的 `lab` 测试(`lab.mon`、`lab.map`)不在默认运行中。

构建与测试命令见上(`cmake` + `ctest`)。CI(`.github/workflows/harness.yml`)跑四种组合:gcc、clang、带 ASan+UBSan 的构建、以及仅编译的 `-m32` 与 iPXE 编译选项,另加 clang + libFuzzer 每个目标 30 秒的冒烟。真正做 fuzz 时要同时给核心加覆盖率插桩(`-DCMAKE_C_FLAGS=-fsanitize=fuzzer-no-link`),否则 fuzzer 看不到核心代码的覆盖率,命令见上。`core.budgets` 测试打印三个配置档的内存占用与一次完整会话后各内存池的峰值,超出文档规定的预算就失败;区域按公布大小精确分配并带护栏,越界写会被发现。`core.docs` 测试核对文档与代码树是否一致(内存表、文件行数、fuzz 种子、测试名、SPDX、CI 工作流)。fuzz 整机目标把每个输入用两种不同的内存填充各跑一遍,可观察行为必须完全一致,以此发现读未初始化内存。CI 另有优化构建上的 no-libc / no-globals 检查和调用深度 / 栈用量检查。

第三部分(对象读写,里程碑 6 至 8)的加固:`osd.hardening` 测试核对七个 fuzz 目标(`fuzz_osd_reply`、`fuzz_osd_backoff`、`fuzz_rbd_cls`、`fuzz_osd_sess`、`fuzz_osd_req`、`fuzz_rbd_open`、`fuzz_client_osd`)及其种子、CI 冒烟任务、`fuzz_long.sh -p partc`、两份 README、调用栈预算(含经 msgr2 上层函数表的回复路径)、故障脚本 `tools/osd_fault_lab.sh`(只创建并删除 `wrtest-ofl-*` 镜像,在实验集群上让核心做随机读写的同时停止或 SIGKILL OSD、标记 out 再 in、用 `pg-upmap` 移动 primary,把每个字节与模型和官方 `rbd export` 比对,并还原集群)以及设计文档 31.3 与路线图。长时间 fuzz 约 3.9 亿次执行,核心无崩溃;故障运行 8 轮、共 9.6 万次随机读写,0 字节差异。
